# laravel-znuny 1.0.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove what does not rest on stock Znuny, correct the API before it is frozen, write down what semantic versioning covers, and add the project files a dependable library needs; release as a candidate first.

**Architecture:** No new subsystem. The lookups and their cache are deleted. The client gets one internal way to mark a failure as handled, which replaces the special case for expired sessions. Settings are read through `Support\Setting` everywhere. The promise lives in the README and is guarded by a test that lists the public classes.

**Tech Stack:** PHP 8.3+, Laravel 12/13 components, PHPUnit 12, Orchestra Testbench 10/11 (Mockery comes with it), PHPStan 2 (level 8), Pint; Znuny 6.5.26/7.0.19/7.1.7/7.2.3/7.3.8 in Docker for the integration suite.

**Spec:** `docs/superpowers/specs/2026-11-27-v1.0-design.md`

## Global Constraints

- PHP `^8.3`, Laravel `^12.0 || ^13.0`; no new dependency in `require`.
- PHPStan level 8 on `src` without baseline and without ignore comments (`composer analyse`); Pint (`vendor/bin/pint --test`).
- A first-class API exists for an operation if, and only if, Znuny ships that operation.
- `Znuny::shouldReceive()`, Mockery mocks of the manager, the resources and `TicketBuilder`, and `Znuny::fake()` keep working. No service class becomes `final`.
- No removal may change behaviour silently. The input key `customerUserID` of `create()` and `update()` stays.
- Every breaking change is listed in `UPGRADE.md` under "0.4.x → 1.0" with old and new behaviour.
- New support classes are `final` and marked `@internal`.
- Tests are written first and watched failing. The test cache serializes and reads no objects back (`tests/TestCase.php`).
- Repository artifacts (code, comments, commits, PR texts, docs) are English. Commits use the repo-local identity `Vitalis Feist-Wurm <hello@itsjustvita.com>`; check `git config user.email` before the first commit. No employer or internal application names anywhere.
- Integration tests need a running Znuny: `tests/Integration/docker/setup.sh` (default image 7.3.8), variables as printed by the script. Tasks that add or touch integration tests run the suite on the instance that is up; before the pull request it runs on 7.3.8 and on 6.5.26. CI runs all six jobs.
- **Not done without the maintainer's explicit approval of that step:** a change to the repository's settings on GitHub, deleting a remote branch, pushing to `main`, a tag, a release. Task 9 lists them.

## Review Focus

1. A config file published by an earlier release that still contains the `cache` block: the package boots, ignores it, and `Znuny::tickets()` works. Test in Task 1.
2. Code written for 0.4 that reads a renamed property with `??`, `isset()` or `pluck()` (`$entry->createTime ?? null`, `collect($history)->pluck('createBy')`): no exception, the fallback value; a plain read throws an `Error` that names the new property. Test in Task 2.
3. The four ways `search_limit` can arrive: `null` (off), a blank string (500), a config file published by 0.2.2 whose `env('ZNUNY_SEARCH_LIMIT')` is null (off), and a connection's blank value over a global null (off, the global value). Test in Task 3.
4. A failure inside a handled scope that the scope does not handle (a 502 while `findMany()` fetches a batch): it is still an error entry and a `ZnunyRequestFailed`; and a Znuny call made by an event listener during a handled failure does not switch the handling off. Tests in Task 4.
5. An application test that mocks instead of faking: `Znuny::shouldReceive('tickets')`, `Mockery::mock(TicketResource::class)`, a partial mock of `ZnunyManager`. Test in Task 6.
