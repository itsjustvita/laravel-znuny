# laravel-znuny v0.3.0 — Convenience and API cleanup

- **Date:** 2026-11-06
- **Status:** Draft for review. The scope follows the roadmap approved in conversation on 2026-11-06; details marked "my call" were decided by the author of this document and are open to change.
- **Target release:** `v0.3.0` (breaking changes are allowed in `0.x` minors)
- **Builds on:** `v0.2.2` plus the CI work on `main` (integration suite against Znuny 6.5, 7.0, 7.1, 7.2, 7.3; PHPStan level 8)

## 1. Why

0.2.x made the package correct against any Znuny: routes, authentication, time zones, sessions, error mapping. What is left is friction in daily use:

- Half of the search filters need `->query()` first, and common filters (ticket number, title, owner, customer user) only exist as raw `where('…')` calls.
- Typical ticket actions (lock, assign, move, set pending) need the caller to know Znuny's parameter names, and a pending time has to be built by hand in Znuny's time zone.
- Applications cannot test their Znuny code without knowing the REST routes and response shapes, because the only tool is `Http::fake()`.
- Setting up the web service in Znuny is manual and depends on the Znuny version; the webhook requester takes four manual steps.
- A few API warts remain from 0.1: mutable dates inside read-only DTOs, one inconsistently named property, a deprecated alias.

0.3.0 removes that friction and switches on the search limit that 0.2.2 introduced as an opt-in.

## 2. Goals

1. Every search filter is reachable from `Znuny::tickets()` directly, and the common filters have named methods.
2. Common ticket actions are one call with Laravel types, including a pending time given as a date.
3. An application can fake Znuny at the level of operations and assert what was called, without HTTP details.
4. One artisan command writes a web service file that Znuny imports and that matches the connection's routes, including the webhook requester.
5. The remaining API warts are fixed in one breaking release with a clear upgrade path.
6. Everything new is covered by unit tests and, where Znuny's behaviour matters, by the integration suite on all five Znuny lines in CI.

## 3. Non-goals

- Lookups (queues, states, priorities, types, customers) without custom Znuny operations. Znuny ships no such operations; that needs a Znuny add-on and is a separate project.
- Iterating beyond the search limit by paging through creation-time windows. The search limit plus its exception keeps results correct; transparent paging can come later.
- Dynamic field types for dates. Needs live verification of Znuny's formats first.
- Typed helpers for `TimeAccountingGet` and `OutOfOffice`, a logout helper, FAQ or ITSM resources. `Znuny::call()` covers them.
- Changing what `get()`, `paginate()` and `lazy()` load by default (articles and dynamic fields). Changing it would empty `$ticket->articles` silently in existing code.

## 4. Anti-goals

- No silent behaviour change. Every breaking change either fails loudly (type error, exception, deprecation notice) or is listed in `UPGRADE.md` with the old and the new behaviour.
- No new option in a nested config block without the one-level merge in the service provider (lesson from 0.2.2).
- No feature that only works on some of the five supported Znuny lines without saying so in the README.

## 5. Features

### 5.1 Search

**Forwarding.** `TicketResource` forwards unknown methods to a new `TicketBuilder` (`__call`) and declares `@mixin TicketBuilder`, so IDEs and PHPStan see the builder's methods on `Znuny::tickets()`. The four existing forwarders stay.

```php
Znuny::tickets()->whereDynamicField('OrderId', 'ORD-*', 'Like')->ids();   // no ->query() needed
```

**New filters on `TicketBuilder`.** Each maps to one documented `TicketSearch` parameter; lists are accepted wherever Znuny accepts them.

| Method | Znuny parameter |
|---|---|
| `whereTicketNumber(string\|array)` | `TicketNumber` |
| `whereTitle(string\|array)` | `Title` |
| `whereType(string\|array)`, `whereTypeId(...)` | `Types`, `TypeIDs` |
| `whereStateId(...)`, `wherePriorityId(...)` | `StateIDs`, `PriorityIDs` |
| `whereOwnerId(...)`, `whereResponsibleId(...)` | `OwnerIDs`, `ResponsibleIDs` |
| `whereCustomerUser(string\|array)` | `CustomerUserLogin` |
| `whereLock(string\|array)` | `Locks` |
| `whereService(string\|array)`, `whereSla(string\|array)` | `Services`, `SLAs` |
| `whereClosedAfter(DateTimeInterface)`, `whereClosedBefore(...)` | `TicketCloseTimeNewerDate`, `TicketCloseTimeOlderDate` |
| `wherePendingAfter(...)`, `wherePendingBefore(...)` | `TicketPendingTimeNewerDate`, `TicketPendingTimeOlderDate` |
| `whereFullText(string)` | `Fulltext` |
| `includeArchived()`, `onlyArchived()` | `SearchInArchive` = `AllTickets`, `ArchivedTickets` |

Dates are converted to the connection's time zone like the existing date filters.

**`count(): int`.** Number of matching tickets, from `ids()`, so the search limit applies.

**`findByNumber(string $ticketNumber, …): Ticket`.** Searches the exact ticket number with `Limit => 1` and loads the ticket with the same options as `find()`. Throws `TicketNotFoundException` when no ticket matches. Customers and e-mail subjects refer to ticket numbers, not IDs.

**Raw `TicketGet` options.** `find()` and `findMany()` get a last parameter `array $options = []` that is merged into the request, for example `['Extended' => 1, 'ArticleLimit' => 5, 'ArticleOrder' => 'DESC']`. The builder gets `withOptions(array $options)` for `get()`, `paginate()` and `lazy()`. *My call:* raw options instead of one named parameter per Znuny flag; the three existing booleans stay.

### 5.2 Ticket actions

On `TicketResource`, all through `TicketUpdate`:

```php
Znuny::tickets()->lock('12345');
Znuny::tickets()->unlock('12345');
Znuny::tickets()->assign('12345', 'agent-login');          // Owner
Znuny::tickets()->move('12345', 'Second Level');           // Queue
Znuny::tickets()->setPending('12345', now()->addDays(3));  // State "pending reminder" + pending time
Znuny::tickets()->setPending('12345', $until, 'pending auto close+');
```

**Pending time as a date.** `pendingTime` in `create()` and `update()` accepts a `DateTimeInterface` besides Znuny's raw hash. It is converted to `Year`, `Month`, `Day`, `Hour`, `Minute` in the connection's time zone, which is how Znuny reads the hash. Znuny only accepts a pending time together with a pending state, so `setPending()` sends both.

**`Ticket::$pendingUntil`.** A new nullable date on the DTO, read from `RealTillTimeNotUsed` (a Unix time, so independent of time zones); `null` when the ticket is not pending.

*My call:* no `setState()`/`setPriority()` helpers; `update($id, ['state' => …])` is already one call.

### 5.3 `Znuny::fake()`

Fakes Znuny at the level of operations. Resources, builders and DTO mapping stay real, so application tests run through the same code as production.

```php
$znuny = Znuny::fake([
    'TicketSearch' => ['TicketID' => ['42']],
    'TicketGet'    => Znuny::fakeTickets(['TicketID' => '42', 'Title' => 'Printer on fire']),
    'TicketCreate' => fn (array $payload) => ['TicketID' => '43', 'TicketNumber' => '2026110643'],
    'TicketUpdate' => new ZnunyAccessDeniedException('TicketUpdate: no permission'),
]);

// … run application code …

Znuny::assertCalled('TicketCreate', fn (array $payload) => $payload['Ticket']['Queue'] === 'Support');
Znuny::assertCalledTimes('TicketGet', 1);
Znuny::assertNotCalled('TicketUpdate');
Znuny::assertNothingCalled();
```

- **Responses** per operation: an array, a closure `(array $payload, string $connection): array`, a `Throwable` to throw, or a list of those wrapped in `Znuny::sequence(...)` that is consumed call by call.
- **Missing fakes fail.** Calling an operation without a fake throws an exception that names the operation. *My call:* strict by default, like `Http::preventStrayRequests()`.
- **`Znuny::fakeTickets(array ...$tickets)`** builds a `TicketGet` response; each ticket is merged over defaults that make `Ticket::fromZnunyResponse()` produce a complete DTO.
- **Implementation.** `Znuny::fake()` swaps the facade root for a `FakeZnunyManager` whose connections all return one `FakeZnunyClient`. The fake client overrides `call()`, records `(connection, operation, payload)` and never sends HTTP. Lookup caching is off. Domain events (`ZnunyTicketCreated`, …) are still dispatched by the resources; request events are not.
- **Assertions** use `PHPUnit\Framework\Assert`, as Laravel's own fakes do.

### 5.4 `znuny:webservice`

```bash
php artisan znuny:webservice                       # default connection, prints YAML
php artisan znuny:webservice tenant-a --output=storage/app/znuny-webservice.yml
php artisan znuny:webservice --webhooks=TicketCreate,ArticleCreate --webhook-url=https://app.example.com
```

Writes a web service definition that Znuny imports under Admin → Web Services → Add Web Service → Import web service (or `Admin::WebService::Add` on the console).

- **Provider.** One operation and route per entry of the connection's route map. Operation types come from a fixed table of Znuny's stock operations (`SessionCreate` → `Session::SessionCreate`, `SessionDelete` → `Session::SessionRemove`, `TicketGetList` → `Ticket::TicketGet`, …). Operations the package does not know (custom ones in the route map) are left out and listed in a warning, because their type cannot be guessed.
- **Requester.** With `--webhooks`, one `Ticket::Generic` invoker for the given events that posts to `{webhook-url}/{webhooks.route_prefix}`. The event name is read from the payload, so one invoker serves all events. The token header is written only with `--with-token`; otherwise the file contains a placeholder and the command says where to put the token. *My call:* secrets stay out of the file by default.
- **Format.** The YAML is rendered from PHP arrays by a small writer in the package; no new dependency. The files the integration suite imports today (`operation-name-webservice.yml`, `webhook-requester.yml`) show the format works on Znuny 6.5 to 7.3.
- **Proof.** `tests/Integration/docker/setup.sh` generates the operation-name web service and the webhook requester with this command instead of importing the two static files. CI then proves on all five Znuny lines that the generated files import and work.

The README's setup section shrinks to: Znuny 6.5.11+/7.1.3+ import the Ready2Adopt example; any other version, any other route layout and webhooks use the generated file.

### 5.5 Attachments

```php
Attachment::fromUploadedFile($request->file('photo'));
Attachment::fromStorage('tickets/photo.jpg', disk: 's3');
```

Both return an `Attachment` with filename, content type and content, like `fromPath()`.

## 6. Breaking changes

| Change | Old | New | How code notices |
|---|---|---|---|
| Dates on DTOs | `Carbon\Carbon` | `Carbon\CarbonImmutable` | Type errors where `Carbon` is type-hinted; mutating calls return a new instance |
| Customer user ID on `Ticket` | `$ticket->customerUserID` | `$ticket->customerUserId` | The old name still works through `__get()` and triggers a deprecation; removed in 0.4 |
| Search limit | off (`null`) | `500` | `ZnunySearchLimitExceededException` for searches without `limit()` that match more than 500 tickets |
| `ZnunyClient::request()` | deprecated alias of `call()` | removed | Fatal error on call |

- **Search limit.** 500 is Znuny's own default cut-off, so no search loads more than it did before; the only difference is that a cut-off result becomes an exception. `'search_limit' => null` restores the old behaviour. *My call:* 500 rather than a higher value, because `get()` holds every ticket with its articles in memory.
- **Dates.** `Ticket::$created`, `$changed`, `$pendingUntil`, `Article::$created`, `HistoryEntry::$createTime`. Both classes implement `CarbonInterface`.
- `UPGRADE.md` gets a `0.2.x → 0.3.0` section with one entry per row.

## 7. Testing

- **Unit and feature tests** for every new method, written first: parameter mapping of the filters, forwarding, `findByNumber()`, pending time conversion (including a non-UTC connection), the fake (responses, sequences, strictness, assertions, multiple connections), the YAML writer and command, attachments, the deprecation of `customerUserID`.
- **Integration suite** (runs in CI against Znuny 6.5.26, 7.0.19, 7.1.7, 7.2.3, 7.3.8 and 7.3.8 on Europe/Berlin):
  - search by ticket number, title, customer user, lock and full text; `findByNumber()`;
  - `lock()`, `assign()`, `move()`, `setPending()` with a date, checked through `$ticket->pendingUntil`, also on the Berlin instance;
  - web services generated by `znuny:webservice` are imported by `setup.sh` and used by the existing tests.
- **Static analysis** stays at PHPStan level 8 without baseline.

## 8. Order of work

Each step is releasable on its own and ends with green unit tests, PHPStan and Pint.

1. Breaking cleanups (dates, `customerUserId`, `request()`, search limit default) with `UPGRADE.md`.
2. Search: forwarding, filters, `count()`, `findByNumber()`, raw options.
3. Ticket actions and pending time; `Ticket::$pendingUntil`.
4. Attachments from uploads and storage.
5. `Znuny::fake()`.
6. `znuny:webservice`, then switch `setup.sh` to generated files.
7. README, CHANGELOG, integration tests for steps 2, 3 and 6; release 0.3.0.
