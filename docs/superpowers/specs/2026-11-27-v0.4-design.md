# laravel-znuny v0.4.0 — Everything Znuny ships, nothing else

- **Date:** 2026-11-27
- **Status:** Scope and API sketch approved in conversation on 2026-11-27. Details marked "my call" were decided by the author of this document and are open to change.
- **Target release:** `v0.4.0` (breaking changes are allowed in `0.x` minors)
- **Builds on:** `v0.3.2`

## 1. Why

The maintainer's goal for this package is to become the official Znuny SDK for Laravel. That sets one rule for what belongs in it:

> A first-class API exists for an operation if, and only if, Znuny ships that operation. Whatever works against one installation only stays in that application.

Measured against that rule, 0.3.2 has two gaps and one leftover:

- **Gap: four stock operations have no API.** Znuny 6.5 to 7.3 ship the same ten operations (source checked for 6.5.26, 7.0.19, 7.1.7, 7.2.3, 7.3.8): `Session::SessionCreate`, `SessionGet`, `SessionRemove`, `Ticket::TicketCreate`, `TicketGet`, `TicketHistoryGet`, `TicketSearch`, `TicketUpdate`, `Ticket::TimeAccountingGet`, `User::OutOfOffice`. The package covers six. `SessionGet`, `SessionRemove`, `TimeAccountingGet` and `OutOfOffice` are only reachable through `Znuny::call()`.
- **Gap: dates in dynamic fields.** A `DateTimeInterface` as dynamic field value is sent as an ISO 8601 string in UTC. Znuny accepts a date-time only as `Y-m-d H:i:s` (it compares the value with its own rendering of it, `DynamicFieldValue::ValueValidate`), so the request is rejected, and the time zone would be wrong anyway.
- **Leftover: the lookups.** `queues()`, `states()`, `priorities()`, `types()` and `customers()` call operations Znuny does not ship (`QueueList`, …) and expect a response format only this package defines. They come from 0.1.

Two smaller things from the review of 0.3.1 fit the same release: connections cannot pass HTTP options (proxy, client certificate, extra headers), and `paginate()` does not read the page from the request.

## 2. Goals

1. Every operation Znuny ships has a typed method, a DTO where it returns data, and a test against real Znuny 6.5 to 7.3 in CI.
2. Dates work in dynamic fields the way they work everywhere else in the package: a `DateTimeInterface` goes in, Znuny's format and time zone go out.
3. The lookups are deprecated with a clear replacement and a removal date (1.0). Nothing breaks for people who use them.
4. A connection can carry HTTP options without weakening the guarantees of `verify_ssl` and the timeouts.
5. The removal announced for 0.4.0 happens: `Ticket::$customerUserID`.
6. The README states the rule from section 1 and shows, per operation, which web service and which permission it needs.

## 3. Non-goals

- Operations of Znuny add-ons (FAQ, ITSM). They follow the same rule later, one add-on at a time.
- Freezing the API (`final`, `@internal`, removing the lookups). That is 1.0.
- Finding an agent's ID from a login by scanning tickets. Znuny has no operation for it; the scan is a workaround for one application and stays there.
- SOAP.

## 4. Anti-goals

- A helper that hides how Znuny really behaves. Where Znuny reports success although nothing happened (section 5.3), the documentation says so.
- New requirements for existing users. Nobody has to change their web service, their config file or their permissions to keep using what works in 0.3.2.
- A way to switch off TLS verification or the timeouts through the new HTTP options.

## 5. Approaches

**A. One resource per area, next to `tickets()` (chosen).** `Znuny::session()`, `Znuny::timeAccounting()`, `Znuny::users()`. Typed arguments, DTOs, the same shape as the existing API, and each method can be guarded by an integration test.

**B. One method per operation, named after it** (`Znuny::sessionGet()`, `Znuny::outOfOffice()`). Thin and complete by construction, but it leaks Znuny's naming and parameter formats, which is what the package exists to hide, and it would sit oddly beside `tickets()->find()`.

**C. Helpers for the session only; `call()` recipes in the README for time accounting and out of office.** Least code. But the two rarely used operations are exactly the ones with surprising behaviour (separate web services, special groups, silent success), and a recipe is not tested in CI.

A was chosen in conversation on 2026-11-27.

## 6. Features

### 6.1 Session: `Znuny::session()`

```php
$user = Znuny::session()->user();   // SessionGet
$user->id;          // "5"
$user->login;       // "api-agent"
$user->firstName;   $user->lastName;   $user->fullName;   $user->email;
$user->type;        // "agent" or "customer"
$user->attribute('UserLastLoginTimestamp');   // any other session value

Znuny::session()->logout();         // SessionRemove
```

- `user()` returns the user of the connection, that is the account the application logs in with. It is not the person who uses the application.
- New DTO `Data\SessionUser` with the properties above, `attributes` (session key to value) and `attribute()`. Znuny returns `SessionData` as a list of `{Key, Value, Serialized?}`; values marked `Serialized` are JSON and are decoded. `type` is `agent` for `UserType` `User`, `customer` for `Customer`.
- **Placeholders from the authentication.** Today a route placeholder such as `:SessionID` is filled from the payload only. It will also be filled from the authentication parameters, so `call('SessionGet')` without payload works, and the repeat after an expired session uses the new session ID. This is a general change in `RequestBuilder`; the payload still wins.
- `SessionGet` answers `SessionGet.SessionInvalid` for a session Znuny dropped. The exception mapper already reads that as an expired session, so `call()` logs in again and repeats.
- **Credentials mode** (`auth => credentials`) has no session. `user()` logs in once to get one (the client can already do that) and sends its ID as payload. My call.
- `logout()` removes the session in Znuny and forgets the cached session ID. Without a cached session it does nothing. It sends the session ID together with the credentials, because Znuny up to 6.5.11 and 7.1 authenticates `SessionRemove` with credentials and newer versions with the session. The operation is called `SessionDelete` in Znuny's web service and in the route presets; the method uses that name.
- **Secrets.** Znuny removes `UserPw` and `UserChallengeToken`, but session data holds every user preference, which can include a two-factor secret, and a customer's session carries `UserPassword`, the hash of the password (seen live on 7.3.8). A key names a secret when it contains `password`, `secret` or `token`, or ends with `pw`, case-insensitive; `UserLastPwChangeTime` is not one. In logs and events, the `Value` of a `{Key, Value}` pair with such a key is redacted. The same holds inside values Znuny marks `Serialized`: a customer's session carries the configuration of the customer backend as JSON, which for an LDAP directory or an external database includes the password Znuny connects with; a serialized value that is not valid JSON is redacted as a whole. The DTO leaves these values out, at any depth, so a dumped or logged `SessionUser` cannot leak them; `Znuny::call('SessionGet', …)` still returns everything. My call, changed after the live check: the first draft kept them in the DTO.
- **What the session knows** (live on 7.3.8): an agent's session has `UserID` (a number), `UserLogin`, `UserFirstname`, `UserLastname`, `UserFullname`, `UserEmail`, `UserType` `User`, the user's preferences (for example `OutOfOffice`) and timestamps. A customer's session has `UserID` equal to the login, `UserCustomerID`, the address fields and `UserType` `Customer`. Group memberships are not part of a Generic Interface session.

### 6.2 Time accounting: `Znuny::timeAccounting()`

```php
$entries = Znuny::timeAccounting()->entries('agent-login', $from, $until);   // Collection<TimeAccountingEntry>
$entries->sum('timeUnit');
```

- Operation `TimeAccountingGet` with `TimeAccountingUserLogin`, `TimeAccountingStart`, `TimeAccountingEnd`. The dates are `DateTimeInterface` and are sent as `Y-m-d H:i:s` in Znuny's time zone, like search dates.
- New DTO `Data\TimeAccountingEntry`: `ticketNumber`, `ticketTitle`, `queue` (the queue the ticket was in at that time), `customerId`, `timeUnit` (float), `created` (`CarbonImmutable`), `attributes`. Znuny returns `{"TimeAccountingResult": [{TicketNumber, TicketTitle, TicketCustomerID, Queue, TimeUnit, Created}]}` and no key at all when there are no entries.
- Znuny answers `TimeAccountingGet.NoPermission` unless the user has `rw` in the group `timeaccounting_webservice`. The mapper turns the suffix `NoPermission` into `ZnunyAccessDeniedException`.
- The operation is not part of `GenericTicketConnectorREST`. Znuny ships it as its own web service, `TimeAccountingREST`, with the route `POST /TimeAccountingGet`. That is the route the package uses for unmapped operations anyway, so a second connection whose `base_url` names that web service needs no route configuration.
- **That connection must use `'auth' => 'credentials'`.** `TimeAccountingREST` has this one route and no `/Session`, so the default session login would fail before the operation is sent. Sharing a session obtained through another web service is not built: it would need a new setting and a change to the session cache key for something one line of configuration solves. My call. The README shows both ways: a second connection with credentials, or the operation added to one's own web service (section 6.4), which has the session routes and works in session mode.

### 6.3 Out of office: `Znuny::users()`

```php
Znuny::users()->setOutOfOffice('agent-login', $from, $until);
Znuny::users()->clearOutOfOffice('agent-login');

// Several users at once, also by e-mail address or Znuny's user search:
Znuny::users()->outOfOffice([
    ['email' => 'jane@example.com', 'from' => $from, 'until' => $until],
    ['search' => 'Miller', 'enabled' => false],
]);
```

- Operation `OutOfOffice` with `OutOfOfficeEntries`, a list of `{UserLogin | UserEmail | UserSearch, StartDate, EndDate, OutOfOffice}`. Entry keys of `outOfOffice()` are `login`, `email`, `search`, `from`, `until`, `enabled` (default true). An entry needs exactly one of `login`, `email`, `search`; otherwise `InvalidArgumentException`.
- Znuny stores calendar days. `from` and `until` are sent as `Y-m-d` of the given date in the date's own time zone, without conversion. My call.
- **Works with and without Znuny's mapping.** Znuny ships the operation in the web service `OutOfOffice`, whose inbound mapping builds the entries from a CSV string (`OutOfOfficeEntriesCSVString`) and fails without it. The mapping keeps the rest of the request and replaces `OutOfOfficeEntries` with what it parsed. A web service without that mapping reads `OutOfOfficeEntries` directly. The package sends both, the entries and the same data as CSV. To be confirmed live in both setups before anything else is built on it (section 8).
- Like `TimeAccountingREST`, Znuny's `OutOfOffice` web service has no `/Session` route, so a connection to it uses `'auth' => 'credentials'` (section 6.2).
- **Znuny reports success even when nothing happened.** An entry that matches no user, or more than one, is skipped and written to Znuny's log; the response is the same. No stock operation reads the setting back for another user. The methods return nothing, and the README says this plainly.
- Only agents with `rw` in the group `admin` may call it. Znuny answers `OutOfOffice.AuthFail` with "User needs to be in group admin" or "User needs to be an agent". In session mode the mapper would read `AuthFail` as an expired session and log in again for nothing, so these two messages map to `ZnunyAccessDeniedException`.

### 6.4 `znuny:webservice --also`

`php artisan znuny:webservice --also=TimeAccountingGet --also=OutOfOffice` adds the two operations to the generated web service, with the routes `POST /TimeAccountingGet` and `POST /OutOfOffice` unless the connection's routes map them. They are opt-in because they need special groups and, for `OutOfOffice`, change other users' settings. The generated `OutOfOffice` operation has no inbound mapping. My call.

### 6.5 Dates in dynamic fields

```php
->withDynamicFields(['DueAt' => now()->addDays(3)])                  // create
Znuny::tickets()->update($id, dynamicFields: ['DueAt' => $date]);     // update
Znuny::tickets()->whereDynamicField('DueAt', $date, 'GreaterThan');   // search

$ticket->dynamicField('DueAt')?->date();   // CarbonImmutable in Znuny's time zone, or null
```

- A `DateTimeInterface` is sent as `Y-m-d H:i:s` in Znuny's time zone. That is what a Znuny field of type "Date / Time" stores.
- A Znuny field of type "Date" accepts midnight only. The package cannot see a field's type, so it uses the optional `dynamic_fields` config: a field declared `'type' => 'date'` is sent as `Y-m-d 00:00:00` (its calendar day in the date's own time zone, no conversion). That is the form Znuny stores and accepts for writing and searching alike; it turns a bare `Y-m-d` into it itself, but only when writing. The validator gets the types `date` and `datetime`, which accept a `DateTimeInterface` or a string in Znuny's format. Without a declaration a `DateTimeInterface` is treated as date-time. My call.
- Reading stays raw: `DynamicField::$value` is what Znuny returned. New: `Ticket::dynamicField(string $name): ?DynamicField` and `DynamicField::date(): ?CarbonImmutable`, which parses the value in Znuny's time zone (null for an empty value). The DTO therefore learns the connection's time zone when a ticket is built. My call; without it, reading a date back needs the time zone by hand, which is the mistake 0.2.1 fixed elsewhere.
- `znuny:generate-fields` writes `\DateTimeInterface|string` for the two new types.

### 6.6 HTTP options

```php
'connections' => ['default' => [
    // ...
    'options' => ['proxy' => 'http://proxy.internal:3128', 'cert' => '/etc/ssl/client.pem'],
]],
'http' => ['options' => ['headers' => ['X-Forwarded-Auth' => '...']]],   // for all connections
```

- `options` are Guzzle request options added to every request of the connection. The connection's `options` replace the global `http.options` key by key.
- **Only these options are accepted:** `proxy`, `cert`, `ssl_key`, `headers`, `auth` (HTTP authentication of a reverse proxy in front of Znuny), `force_ip_resolve`, `version`. Any other key raises a `ZnunyConfigurationException` that lists the accepted ones and, for `verify`, `timeout` and `connect_timeout`, names the setting to use instead. An allowlist, because options such as `curl` or `stream_context` can switch off TLS verification and timeouts, and others (`handler`, `http_errors`, `base_uri`) change what the client relies on. The list can grow on request; it could not shrink without breaking configurations. My call.
- `headers` are merged; the package's own headers (authentication) win.
- The values can be secrets (a proxy password, a certificate passphrase). They are never logged and are not part of events or exceptions.
- `http` is one of the blocks merged with the package defaults, so a config file published earlier needs no change.

### 6.7 `paginate()`

`paginate(int $perPage = 25, ?int $page = null)`: without a page it uses the page of the current request (`Paginator::resolveCurrentPage()`), as Eloquent does.

### 6.8 Deprecated: the lookups

- Deprecated: `Znuny::queues()`, `states()`, `priorities()`, `types()`, `customers()`, `flush()`, `flushAll()`, the command `znuny:cache-clear` and the `cache` config block. Each gets `@deprecated` and triggers `E_USER_DEPRECATED` when used, as `Ticket::$customerUserID` did. They keep working until 1.0.
- Replacements in README and UPGRADE: `Znuny::call('QueueList')` for the custom operations, `Znuny::tickets()->whereCustomerId($id)->get()` for `customers()->tickets($id)`.
- The package's own tests of the lookups stay and expect the deprecation.

## 7. Breaking changes

1. `Ticket::$customerUserID` is gone, as announced in 0.3.0. The input key `customerUserID` of `create()` and `update()` stays.
2. `paginate()` without a page follows the request's `?page=`. Callers that relied on page 1 pass `page: 1`.
3. `TimeAccountingGet.NoPermission` and the two `OutOfOffice.AuthFail` messages raise `ZnunyAccessDeniedException` instead of a generic or session exception. Only visible to people who already call these operations through `call()`.
4. A `DateTimeInterface` as dynamic field value is sent in Znuny's format. Before, Znuny rejected it, so nothing that worked changes.

`UPGRADE.md` gets a section "0.3 to 0.4" with these four and the deprecations.

## 8. Testing

- Unit and feature tests for every method, written first.
- **Live first.** Sections 6.1 to 6.3 rest on reading Znuny's source. Before the features are built, the integration setup is extended and each assumption is checked against a real Znuny: the keys `SessionGet` returns for an agent and a customer, `SessionRemove` on old and new versions, `TimeAccountingGet` with and without the group, `OutOfOffice` through Znuny's shipped web service (with mapping) and through a generated one (without). What turns out different changes this document before code is written: the builder amends the affected section within the goals of section 2, notes what was observed on which Znuny version, and goes on. The builder stops and reports to the maintainer only when a goal cannot be met on a supported version. For `OutOfOffice`, Znuny's shipped web service (with the mapping) is the setup that has to work; if sending both forms fails there, the package sends the CSV string only and `znuny:webservice --also=OutOfOffice` generates the operation with the same inbound mapping.
- Integration setup (`tests/Integration/docker/setup.sh`): the group `timeaccounting_webservice`, an agent in `admin`, dynamic fields of type Date and Date / Time, a generated web service with `--also`, and Znuny's shipped `OutOfOffice` web service.
- Integration tests, on all six CI jobs: `session()->user()` returns the configured login; after `logout()` the old session ID is invalid; an article with time units appears in `timeAccounting()->entries()`; `setOutOfOffice()` shows up in that agent's own session data (`OutOfOffice`, `OutOfOfficeStartYear`, …), which is the only stock way to read it back; date and date-time dynamic fields round-trip through create, search and `date()` on a Znuny that does not run on UTC.
- `Znuny::fake()` answers the new operations like any other; the README documents the response shapes.
