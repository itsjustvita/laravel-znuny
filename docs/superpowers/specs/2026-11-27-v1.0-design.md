# laravel-znuny v1.0.0 — A promise that can be kept

- **Date:** 2026-11-27
- **Status:** Scope, the open classes and the release candidate were approved in conversation on 2026-11-27. Details marked "my call" were decided by the author of this document and are open to change.
- **Target release:** `v1.0.0-rc.1`, then `v1.0.0` from the same commit unless the candidate shows a problem.
- **Builds on:** `v0.4.0`

## 1. Why

The maintainer's goal is for this package to become the official Znuny SDK for Laravel. 1.0 is the step that lets others depend on it: from then on a minor release must not break an application. Before that promise is made, three things have to be true.

- **Nothing rests on operations Znuny does not ship.** 0.4.0 deprecated the lookups (`queues()`, `states()`, …) that came from 0.1. They and what hangs on them are removed now, because after 1.0 they could only go in 2.0.
- **What is frozen is worth freezing.** A pass over the public API found a handful of inconsistencies (section 7). They are cheap to fix now and breaking later.
- **The promise is written down.** Today 50 classes are neither `final` nor marked internal, so nobody can tell what may change. The README has to say what semantic versioning covers, and the code has to mark the rest.

A library people depend on also needs a way to report a vulnerability, a contribution guide and a statement of what is supported. None of them exist yet.

## 2. Goals

1. The package has no method, class, setting or command that needs an operation Znuny does not ship.
2. The README states what is covered by semantic versioning and what is not; everything not covered is marked `@internal` in the code, and a test fails when a new class is neither.
3. The API corrections of section 7 and the five minors deferred from the review of 0.4.0 are done.
4. One rule for settings: a blank value counts as not set, everywhere.
5. `SECURITY.md`, `CONTRIBUTING.md`, issue and pull request templates, and a support statement exist.
6. The release is a candidate first.

## 3. Non-goals

- New operations or features (FAQ, ITSM). They come in 1.x, by the rule of 0.4.0.
- Interfaces for the manager or the resources, and `final` on service classes (section 5).
- Approaching the Znuny project. That follows 1.0.
- Changing what `find()` and `get()` load by default (`find()` loads the ticket only, a search loads articles and dynamic fields). Considered: either change would silently cost data or requests for existing callers. The README documents the difference.
- Renaming `usingCredentials()`'s parameters. Its documented call uses the named argument `options:`.

## 4. Anti-goals

- A promise broader than can be kept. Protected members, internals and message wording are not covered.
- Breaking how applications test: `Znuny::shouldReceive()`, Mockery mocks of the manager and the resources, and `Znuny::fake()` must keep working.
- A removal that changes behaviour silently. The input key `customerUserID` of `create()` and `update()` stays for that reason: without the alias the key would pass through to Znuny unchanged, and the ticket would be created without its customer user.
- A change to the repository's settings on GitHub, a tag or a release without the maintainer's explicit approval of that step.

## 5. Approaches

**A. Open classes, a written promise, `@internal` for the rest (chosen).** Manager, client, resources and builders stay non-final, so Laravel's facade mocking and Mockery work. The README lists what is covered. Infrastructure classes get `@internal`. A test pins the list of public classes.

**B. `final` wherever possible.** The smallest surface and the clearest signal. But `Znuny::shouldReceive('tickets')` creates a Mockery mock of the manager, and applications mock resources the same way; both fail for final classes. That breaks a normal Laravel testing pattern for the sake of preventing subclassing, which the written promise excludes anyway.

**C. Contracts.** Interfaces for manager and resources, with the classes final behind them. The cleanest in theory; every new method would then be a breaking change of an interface, and nobody has asked for a second implementation.

A was chosen in conversation on 2026-11-27.

## 6. What is removed

- `ZnunyManager::queues()`, `states()`, `priorities()`, `types()`, `customers()`, `flush()`, `flushAll()`, with their facade annotations.
- `Resources\QueueResource`, `StateResource`, `PriorityResource`, `TypeResource`, `CustomerResource`; the cache parameter, `remember()` and `rows()` of `Resources\Resource`.
- `Data\Queue`, `State`, `Priority`, `Type`, `Customer`.
- `Caching\CacheManager`, the `cache` block of the config, `ZNUNY_CACHE_ENABLED`. `ZNUNY_CACHE_STORE` stays: it also names the store of the session cache (`session.cache_store`).
- The command `znuny:cache-clear`.
- `QueueNotFoundException` and `CustomerNotFoundException`. A not-found error of an operation that is not a ticket operation raises `ZnunyNotFoundException`, their parent.
- The names of custom operations in the client's list of repeatable reads (`QueueList`, `QueueGet`, `StateList`, `PriorityList`, `TypeList`, `CustomerUserGet`) and the `QueueGet` route of the `operation-name` preset. A custom operation on a GET route is still repeated like every GET.
- `TicketBuilder::$limit`, which nothing reads.
- Their tests, the README section "Lookups (deprecated)" and the troubleshooting rows about them. `UPGRADE.md` keeps the table of replacements.

Kept on purpose: the input key `customerUserID` (section 4); `usingCredentials()`; the `operation-name` preset; the mapper's heuristics for error codes Znuny's core does not use, because they give `Znuny::call()` of a custom operation sensible exceptions.

A config file published earlier may still contain a `cache` block. It is ignored.

## 7. API corrections before the freeze

Items 1 to 4 come from a pass over the public API. Items 5 to 9 are the five minors deferred from the review of 0.4.0.

1. **Ticket IDs are `string|int`** in every method of `TicketResource` that takes one (`find()`, `update()`, `addArticle()`, `close()`, `lock()`, `unlock()`, `assign()`, `move()`, `setPending()`, `history()`). Applications keep IDs as integers; with `declare(strict_types=1)` they get a `TypeError` today. A widening, so nothing breaks.
2. **`HistoryEntry::$createTime` becomes `$created`, `$createBy` becomes `$createdBy`.** Every other object says `created`. My call.
3. **Every data object fails on an undefined property**, as `Ticket` does: reading one throws an `Error`, `isset()` and `??` are false. The guard moves into the shared trait, and a renamed property's error names the new one (`createTime`, `createBy`, and `Ticket`'s `customerUserID`). My call: one behaviour for all of them, and a typo in a property name should not read as null.
4. **One rule for blank settings.** A setting that is null or a blank string counts as not set and takes its default: `default`, `auth`, `user_type`, `auth_transport` of a connection, `logging.enabled`, `logging.channel`, the three `logging.log_*` switches, `session.auto_retry_on_expired`, `webhooks.enabled`. The same holds for `session.cache_prefix`, `webhooks.route_prefix` and `webhooks.auth.header`; `routes`, `timezone`, `verify_ssl`, the numbers and `session.cache_store` already follow it. Switches read `"false"`, `"off"`, `"no"` and `0` as off. Today a blank `ZNUNY_AUTH=` is a configuration error and a blank `ZNUNY_LOGGING_ENABLED=` switches logging off; both change.

   Two settings differ, and the README says so:
   - `webhooks.auth.type`: a blank type keeps rejecting every webhook, because that setting must fail closed.
   - `search_limit`: `null` is a value of its own and switches the limit off (`ZNUNY_SEARCH_LIMIT=null`, and config files published by 0.2.2, which contain `env('ZNUNY_SEARCH_LIMIT')`). A blank string, as an empty `ZNUNY_SEARCH_LIMIT=` gives, used to switch it off too; from 1.0 it means the default of 500. My call: an empty variable should not silently switch off the check that a search is complete, for the same reason an empty timeout must not mean waiting forever. The cost is a `ZnunySearchLimitExceededException` for an installation that relied on the blank value; it names the setting, and `UPGRADE.md` lists the change.
5. **A failure the package handles itself is no error.** It is logged as information and fires no `ZnunyRequestFailed`, like the expired session in session mode since 0.3.2. This is a rule, and it holds in every place where the package catches a Znuny failure and goes on:
   - `logout()` when Znuny answers `SessionRemove.Fail`;
   - `session()->user()` in credentials mode when the cached session is gone;
   - `findMany()`, and with it `get()`, `paginate()` and `lazy()`, when Znuny rejects a batch because one ticket is unreadable and the package splits the batch;
   - `create()->save()` when the new ticket cannot be read back. The warning it logs stays; the error entry and the event of the failed read go.

   `ZnunyRequestFailed` and the error log then mean: a failure reached the application. The README's sections on events and logging say so.
6. **`session()->user()` raises `ZnunyServerException`** when Znuny's response has no `SessionData`, instead of returning a user without login.
7. **`outOfOffice()`** trims `login`, `email` and `search` and refuses an entry whose `from` is after its `until`.
8. **`options`:** `headers` must map header names to values (a list is refused); `'headers' => null` means none; `Content-Type` cannot be configured, because the package sets it; `cert` and `ssl_key` must name existing files (a path, or `[path, passphrase]`), checked when the connection is built, like `verify_ssl`.
9. **A live test for special characters in out-of-office entries:** through Znuny's own web service, one call with an entry whose `search` contains a comma and quotes, followed by an entry for a real agent. The second entry only arrives intact if the CSV kept the first in its field.

## 8. The promise

A README section "Stability" with this content.

**Covered by semantic versioning** (a breaking change needs a new major version). For a class named here, every public member is covered unless it is marked `@internal`; the list names what people use most, it does not limit the cover:

- the `Znuny` facade and the public methods of `ZnunyManager`;
- the resources `tickets()`, `session()`, `timeAccounting()`, `users()` and the builders they return: public methods and documented behaviour;
- of `ZnunyClient`: `call()`, `ping()`, `sessionId()`, `logout()`, `connection()`, `settings()` (the read-only properties of `ConnectionConfig`) and `routes()` (`route()`, `has()`, `all()`, `preset()`);
- the data objects (`Ticket`, `Article`, `Attachment`, `DynamicField`, `HistoryEntry`, `SessionUser`, `TimeAccountingEntry`): public properties and methods, among them `attribute()`, `toArray()`, `fromZnunyResponse()`, `Ticket::dynamicField()`, `DynamicField::date()` and the `Attachment::from…()` factories, and construction with named arguments;
- the events: class names, public properties and methods (`ZnunyWebhookReceived::is()`, `ticket()`), and construction with named arguments, so that application tests can build one;
- the exceptions: class names, their hierarchy, construction, the getters, the setters and `context()`, so that application tests can build a Znuny error;
- `ConnectionConfig` as returned by `settings()`: its properties, constants and `usesSession()`; `RouteMap` and `Route` as returned by `routes()`: their reading methods and properties; `RoutePresets`' constants;
- `ZnunyServiceProvider` and `registerWebhookRoutes()`; `Testing\FakeResponseSequence` as the return type of `Znuny::sequence()`, without its methods;
- the config keys, their defaults and the environment variables;
- the artisan commands: names, arguments, options and exit codes;
- webhooks: the route name and middleware alias `znuny.webhook`, `WebhookController` as a route action, `ZnunyWebhookReceived`;
- testing: `Znuny::fake()`, `fakeTickets()`, `fakeSessionUser()`, `sequence()`, the assertions, `recorded()`, `StrayZnunyCallException`;
- the route presets' names.

**Not covered:**

- everything marked `@internal`;
- protected and private members, and subclasses of the package's classes;
- the positional order of constructor parameters;
- the wording of log entries, exception messages and command output, and the exact content of a generated web service file;
- what `Znuny::call()` returns: that is Znuny's response.

**Policy.** My calls, to be read by the maintainer as commitments:

- A deprecation is announced at least one minor release before the removal, with `@deprecated`, a deprecation notice and an entry in `UPGRADE.md`.
- Dropping a version of PHP, Laravel or Znuny that its maker no longer supports happens in a minor release and is named in the CHANGELOG. Composer keeps an application on the last release that fits it.
- Fixes go into the latest 1.x release. There is no long-term support branch.
- Tested in CI: PHP 8.3 to 8.5, Laravel 12 and 13, Znuny 6.5, 7.0, 7.1, 7.2 and 7.3.

**In the code.** `@internal` on: `Http\*`, `Session\*`, `Support\*`, `DynamicFields\*`, `WebService\*`, `Exceptions\ExceptionMapper`, `Builders\TicketInputMapper`, `Webhooks\WebhookPayload`, `Webhooks\AuthenticateWebhook`, the `Commands\*` classes, `Testing\FakeZnunyClient`, `Testing\FakeZnunyState`, `Resources\Resource`; on the constructors and factories of `ConnectionConfig`, `RouteMap`, `Route`, `ZnunyClient`, the resources and the builders; and on the methods `ZnunyClient::identityKey()`, `cachedSessionId()`, `forgetSession()`, `warn()`, `TicketResource::fetchOptions()`, `ConnectionConfig::identityKey()`, `loginKey()`, `timezoneFor()`. `Testing\FakeZnunyManager` is public for its assertion methods only; `FakeResponseSequence::isEmpty()` and `next()` are internal.

## 9. Project files

- **`SECURITY.md`:** report through GitHub's private vulnerability reporting ("Report a vulnerability" on the repository's Security tab), what to include, which versions get fixes (the latest 1.x). No e-mail address. This needs the setting switched on in the repository (section 10).
- **`CONTRIBUTING.md`:** the rule that decides what belongs in the package, how to run the unit suite and the integration suite, Pint and PHPStan, tests first, where designs and plans live.
- **Issue templates** (`.github/ISSUE_TEMPLATE`): a bug report that asks for the package version, the Znuny version, the web service or route preset and the authentication mode, and reminds people to remove secrets; a feature request that asks which Znuny operation it is about; a `config.yml` that points security reports to the policy. A pull request template with the checks.
- **`composer.json`:** remove `minimum-stability` and `prefer-stable`.
- **`.gitattributes`:** keep `CONTRIBUTING.md` out of the package archive.
- **README:** the "Stability" section, the support statement next to the requirements, no lookups section; `UPGRADE.md` "0.4.x → 1.0"; CHANGELOG.

## 10. Steps that need the maintainer's approval

Each is named in the plan as a stop, not done on the way:

- setting the repository's topics (`laravel`, `znuny`, `otrs`, `php`, `sdk`, `helpdesk`, `generic-interface`);

## 11. Release

- The CHANGELOG gets a section `[1.0.0-rc.1]`. The tag is published on GitHub as a pre-release. Composer installs it only when asked for (`^1.0@RC`), so applications on `^0.4` are not moved.
- The candidate stays until the maintainer's application has run on it. A problem found then is fixed and released as `rc.2`. Without one, `v1.0.0` is tagged on the same commit, with the CHANGELOG section renamed in a commit of its own.

## 12. Testing

- Every change comes with a test written first. Removals are proven by the suite staying green and by a test that the removed methods and classes are gone.
- **A test of the promise:** `PublicApiTest` lists the classes that are public. It fails when a class in `src` is neither in that list nor marked `@internal`, so adding a class forces the decision.
- **A test of the anti-goal:** `Znuny::shouldReceive('tickets')` and a Mockery mock of `TicketResource`, `SessionResource`, `TimeAccountingResource`, `UserResource` and `TicketBuilder` work.
- The integration suite runs unchanged on all six CI jobs, plus the case of section 7.9.
